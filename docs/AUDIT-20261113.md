## 2. 三条系统性病根（比"文件太大"严重得多）

### 病根 A：没有唯一权威中间表示

`targetY` / `spans` / 桥范围是**三套并行事实**，写入点 2~8 个，靠"跑完再校验再修"收敛，不靠不变量。

- `computeTargetY` 调 **6 次**（`Road:185/195/212/269/659/674`），每次内部 **15 道 pass**
- 跨度提取/重分类 **14 次**（`Road.java` 8 处 + `RoadPlanConsistencyService` 4 + `RoadSnapService:250` + 建造期 2）
- 纵向平滑 **≥6 套并存**（`RoadGradePlanner:464`、`TargetY:379/383/405`、`RoadDataValidator:236/334`、`PathPostProcessor:815`、`NetworkReuseMerger:685`）
- 施工阈值 **挖深 5/8/32/64 四套、填深 2 vs 5 两套**（`RoadConstructionSafety:41-82`）⇒ 规划按 5 钳、验收按 32 判，**配置语义对不上**
- 取高度 **7 条并行实现**，高度口径在 5 个类各写一遍
- 9 处 `new PriorityQueue<` ⇒ **9 套独立 A\***，四寻路器只是同一内核换扩展顺序

### 病根 B：指标算出来但不进决策

- `TunnelEnvelopeCriterion` 已算出 tunnel/switchback/climb 三条 A\* 量纲代价，但 `elected` 只由几何三门决定，**代价只用来写 `why`**（类注自述"只打数、不参与选址"）
- `QualityGate` 设计为质量闸门，**零调用**
- `FinslerMetric.cost()` 算得出各向异性，**没人用**

### 病根 C：契约断裂 + 静默降级

| 断裂 | 后果 |
|---|---|
| `FinslerMetric:35` / `ObstaclePotential:32` 都写"硬约束由 band 投影负责"，但 **`ElasticBandSolver` 完全不认识 `TerrainField`/`ObstacleField`** | **硬约束没人做** ⇒ band 会把曲线拉进山体/建筑 |
| `ArrivalTimeField` **不查 `isPassable`**，只做 8 邻域 max 下降 | 路径 45° 量化、可切角穿建筑 |
| `shouldAvoidPlanning` 取不到 ThreadLocal 快照时返回 `PlanningSnapshot.EMPTY` | **全链静默"什么都不挡"**，与"附近真没建筑"同形 —— 最难查的一类 bug |
| `RawPathSearch:306` 失败后静默降级重搜 | 每次白跑一遍全场 FMM |
| `BandPathfinder.findRawPath` 传 `width=1` ⇒ `clearance=0` | 硬避让半径归零 |
| `RoadBlockPlacer:87` 无条件 `setBlock(pos.below())`，保护判定只在调用点 | 其它调用者可直接覆盖受保护方块 |

## 追加更正（2026-11-13，S2 复核）

**§3 里把 `promoteRuntimeBridges` 记为「每区块重算桥范围」是错的。**

复核源码后的实际情况：

| 事实 | 位置 |
|---|---|
| 有 Streams 时直接短路返回 | `RoadConstructionSafety:432` |
| 只对「距当前处理区块 N 区块以内」的站做世界探测 | `inWindow(...)`，`:911` |
| 已规划的桥跳过，不重复探测 | `:443` |
| 探测结果增量累积并按路线身份去重 | `RUNTIME_BRIDGES.compute(...)`，`:466` |

⇒ 它是 **O(窗口) 的增量探测**，不是 O(路线 × 区块)。O(n) 那部分只是一次数组遍历。

**它的存在理由是信息差**：没有 Streams 时，规划期无法预知某些水体会在区块生成之后才出现；
它是「别把半边河床填平」的安全网。**已从「待消除的技术债」改判为「设计必需」。**

> 意义：如果按错误判断去"优化"它，会删掉一个真正的安全网。
> 教训是 —— 台账必须逐条核对**真实成本**，不能凭调用位置推断。
