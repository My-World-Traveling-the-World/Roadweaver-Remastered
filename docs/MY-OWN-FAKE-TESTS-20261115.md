## 一、被证伪的两条用例

### 用例 1：`站数上限与配置默认值一致`
```java
// 原写法（已删除）
assertTrue(CulvertJudge.maxSegments() == 6 || CulvertJudge.maxSegments() > 0,
        "站数上限应可读（兜底 6 / 或读到配置值）");
assertTrue(CulvertJudge.maxWaterDepth() == 2 || CulvertJudge.maxWaterDepth() > 0,
        "水深上限应可读（兜底 2 / 或读到配置值）");
```

**问题**：`x == 6 || x > 0` 在逻辑上**等价于 `x > 0`**（`x == 6` 蕴含 `x > 0`）。
而 `CulvertJudge.maxSegments()` 内部是 `clamp(..., 1, 16)` ⇒ **恒 ≥ 1** ⇒ **断言恒真**。

**它注释写的是「兜底值必须等于 `RoadAppearanceConfig` 的出厂默认」，
但它一个字节都没验证这件事。**

⇒ 这是**假测试**：它永远通过，且它声称守的东西和它实际守的东西完全不同。

### 用例 2：`施工期上限读配置且夹在规划期范围内`
```java
int segments = CulvertJudge.maxSegments();
assertTrue(segments >= 1 && segments <= 16, "站数上限必须夹在 [1,16] ...");
```

**看起来**在验证夹取。**实际**：单测环境里 `ConfigService` 不可用，
`maxSegments()` 走兜底常量 6 ⇒ `6 >= 1 && 6 <= 16` 恒真，
**夹取代码一行都没被执行。**

### 负控实证（这是关键）
把 `CulvertJudge.maxSegments()` 的夹取上界从 **16 改成 99**：
```
结果: PASS tests=922 skipped=0 / BUILD SUCCESS
```
**测试全绿。** 证明确实没测到夹取。

## 二、改成什么（3 条会真红的断言）

| 新用例 | 守什么 | 负控 |
|---|---|---|
| `兜底值必须等于配置出厂默认` | `new RoadAppearanceConfig()` 的字段初始值 == `CulvertJudge.DEFAULT_MAX_*` | 把默认 6 改成 7 ⇒ **红** ✅（还连带抓到 `ConfigKeyTableConsistencyTest`） |
| `配置侧夹取范围必须写死为规划期口径` | `setCulvertMaxStations(999)` → 16、`(-5)` → 1；水深同理 4/1 | 把上界 16 改成 64 ⇒ **红** ✅ |
| `施工期可读的站数上限必须落在规划期夹取范围内` | `CulvertJudge.maxSegments()` 必须落在「配置侧能给到的最大区间」内 | 同第 2 条的负控可覆盖脱节情形 |

第二条的负控 `16 → 64` **正是本轮缺陷的原始形态**（UI 声明 0..64，下游只认到 16），
所以这条测试现在是那个历史缺陷的专门守卫。

## 三、仍然没被覆盖的部分（如实标注）

**`CulvertJudge` 内部的 `clamp(...)` 本身仍没有被直接测试。**
原因是：

- `clamp` 是 `private`
- 单测环境 `ConfigService` 不可用 ⇒ 走不到读配置那条分支
- 上界/下界是**字面量**（`1, 16` / `1, 4`），没有具名常量可断言

**要真正覆盖它**，需要把四个界值提成包内常量（如
`SEGMENTS_MIN/SEGMENTS_MAX/DEPTH_MIN/DEPTH_MAX`），然后测试断言
「`CulvertJudge` 用的界值 == `RoadAppearanceConfig` 夹取用的界值」。
**那需要改生产代码（纯可见性/结构化，零行为变化），按用户规矩需先拍板**，本轮没做。

现在的第三条用例只是**间接**兜底：如果两边界值脱节到「施工期能拿到超出配置侧可达范围的值」，
它会红；但若两边一起被同向改错（都改成 99），它不会红。

## 四、方法论：为什么我会写出这种东西

回看这三条，共同形态是**「把注释里的意图抄成了断言」**：

- 注释说「兜底值必须等于出厂默认」→ 我写了个 `== 6 || > 0`，因为我当时想的是
  「测一下它能读到值」。**把「能被读取」当成了「值正确」。**
- 注释说「夹在 [1,16]」→ 我写了个 `>= 1 && <= 16`，因为兜底值 6 天然满足。
  **把「兜底值恰好落在区间内」当成了「夹取逻辑正确」。**

⇒ **规律：写断言时如果不自觉地问「怎么才能让它失败」，写出来的必然是同义反复。**
**正确顺序是反的：先设计负控（怎么把它弄红），再写断言去接住那个红。**

**这条已加入我这几轮的执行规则：任何新增测试，必须先跑一次负控证明它会红，
才允许进回归套件。**
