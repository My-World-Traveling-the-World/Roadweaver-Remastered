## 〇、一句话结论

**主接线已全部接通，旧算法类已全部删除；但「新内核」还不是生产的唯一参与者**——

## 一、🔴 已证实的严重缺陷（按严重性排序）

### A. 降级重搜时硬障碍完全失效（最严重）

**证据链**：

1. `ObstacleJudge.java` 的 `blocksPlanningObstacle`：
```java
BuildingObstacleMode mode = BUILDING_OBSTACLE_MODE.get();
if (mode == BuildingObstacleMode.PENALTY) return false;   // ← PENALTY 直接返回 false
if (shouldAvoidPlanning(pos, horizontalClearance)) return true;
return mode == BuildingObstacleMode.HARD_BUILDINGS_AND_CLUSTERS
        && blocksVillageCluster(pos, horizontalClearance);
```

2. `RawPathSearch.searchWithHardBuildingObstacles`（`:290-306`）：
```java
try (BuildingObstacleScope ignored = withBuildingObstacleMode(HARD_BUILDINGS_AND_CLUSTERS)) {
    hard = pathfinder.findRawPath(...);          // 第 1 次：硬障碍生效
}
if (hard != null && hard.success() && hard.hasRawPath()) return hard;
return pathfinder.findRawPath(...);              // 第 2 次：mode 已回落到 PENALTY
```

3. `BandPathfinder` 的障碍场构造（`:107-119`）：
```java
blocked[index] = blocksPlanningObstacle(new BlockPos(x, y, z), clearance);  // PENALTY ⇒ 全 false
ObstacleField obstacles = new StridedObstacleField(..., blocked, outOfTerrain);
```

**后果**：第 2 次（降级）重搜时 `blocked[]` **全部为 false**，且 `ObstaclePotential.fromMask` 也从全 false 生成 ⇒ **软势恒为 0**。

也就是说：**降级重搜 = 在完全无障碍的地图上找路**，会直接穿村庄、穿建筑。注释里说的「降级后的结果与改动前完全一致」和「高代价模式」都不成立。

**影响面**：所有需要降级的连接（村庄封死走廊的情况）。

**修法**：`BandPathfinder` 不该依赖 `BuildingObstacleMode` 这个 ThreadLocal 门控 ——
应该像旧版 `PotentialFieldPathfinder` 那样，在自身内部把「硬障碍」和「软势」分开构造，
或者在 PENALTY 模式下改用软势（而不是零势）。

---

### B. 弹性带会把绕障后的点拉回障碍里

**证据**：`ElasticBandSolver.java` 全文 **0 处** `ObstacleField` / `project` / `投影`。

`FinslerMetric` 的类注释写着「硬约束（一定不能穿结构）由 `band` 层的投影负责」
（`FinslerMetric:35`），`ObstaclePotential:32` 也这么写 —— **但没人做这件事**。

**后果**：
- FMM 绕开了障碍（`impassable` 格子不进队列）
- 但 `ElasticBandSolver.smooth()` 只做「保形 + 拉直」，**完全不知道障碍在哪**
- 平滑后曲线可以横穿建筑/山体

**这是「契约断裂」的典型**：两个类都声称由对方负责，实际无人负责。

**修法**：`ElasticBandSolver` 每轮迭代后加一步投影 ——
把落在 `obstacles.impassable(x,z)` 上的点推到最近可行点，并把这一点约束在后续迭代中。

### C. 纵断面是「旧流水线 + DP」双跑，不是替代

**证据**：`TargetYComputation.java:452-464`
```java
int[] legacySnapshot = smoothed.clone();   // 旧流水线的完整结果
// ...
smoothed = applyProfileSolver(level, centers, smoothed, terrainY, isCrossing, tunnelMask,
        pinnedMask, startBoundary, endBoundary, cfg, gradeLimits, connection);  // 再跑 DP
```

`ProfileSolverMode.parse`（`:86-91`）默认返回 `DP`。

**后果**：
- 旧流水线的 15 道 pass **先完整跑一遍**
- 然后 DP **再完整跑一遍**
- 默认端到端成本 = **旧流水线 + DP**，不是「DP 替代旧流水线」
- 且 DP 走二阶分支时复杂度是 **`O(n·H·D²)`**（D=2N+1），不是 `ProfileDpSolver` 类注释声称的 `O(nH)`

**为什么双跑**：`legacySnapshot` 是给 `ProfileAbObserver` 当「legacy 臂」用的（`:516-532`）。
观测本身有价值，但**观测不该阻塞生产**。

**修法**：
- 方案 A：观测降级为采样（只对 N% 的连接双跑，其余只跑 DP）
- 方案 B：DP 与旧流水线择一（用一个开关明确选，不再双跑）
- 方案 C：把「旧流水线」整体删除（符合用户「旧的全部删除」的拍板）

### D. 生产链上仍有 3 处旧式修复搜索（未换新内核）

| # | 类 | 证据 | 性质 |
|---|---|---|---|
| 1 | **`MountainSwitchbackPlanner`** | `findContourRoute:178-240` 自己的 `PriorityQueue` + `f(best)+heuristic`（`:197-202`、`:233-234`）+ 邻居展开（`:205-237`）+ 启发函数（`:317-320`）。全类**无** `PathfinderFactory`/`BandPathfinder` 调用 | 由 `RawPathSearch:68-69` 在 Band 结果后直接调用；候选更好时**直接替换主路线**（`:97-108`）|
| 2 | **`CoarseHeightAwarePlanner`** | `:60-63`、`:136-137`、`:190-195` 也是自己的 `PriorityQueue` + heuristic 3D 搜索 | 由 `RawPathSearch:124-153` 条件触发 |
| 3 | **`LocalRouteSearch`** | `:44-65` 明确是局部窗口 A*；`:407-418`、`:521-524` 是实现 | 由 `AccurateGradeRepairPlanner:285`、`:296` 等生产修复路径调用 |

**后果**：最终路线可能被这几套旧 A* 的修复结果替换，
所以不能宣称「整条生产链只剩新内核」。

**修法**：这三处都要换成 Band/FMM，或明确保留并写清理由（它们是修复机制不是主搜索）。

---

### E. `ArrivalTimeField.pathTo` 不查 `isPassable` + 坐标错位 + maxSteps 未生效

**证据**：
- `ArrivalTimeField.java` 全文 **0 处** `isPassable` / `impassable`
- `pathTo`（`:90-127`）只做 8 邻域 `T` 最小下降
- `BandPathfinder` 的 `maxSteps` 参数**只在签名出现**（`:67`），从未用于限制求解

**后果**：
1. 回溯时可能切角穿建筑（虽然硬格 `T=∞` 通常不会被选中，但 step>1 的线段和弹性带平滑后**无硬保证**）
2. 非网格对齐坐标有 floor/输出偏移错位
3. `maxSteps`（配置的 `aStarMaxSteps=200000`）对 BAND 完全无效 ⇒ 无法限制求解规模

## 二、⚠️ 已证实的中度问题

### F. `PipelinePlanner` 内有条件触发的旧式直线 MST 回退

**证据**：`PipelinePlanner.java`
- `:99-103`（`level == null`）
- `:143-150`（采样 `RuntimeException`）
- `:155-160`（管线 `RuntimeException`）

三处都调 `fallbackMST`（`:206-212` 注释明说「从旧 `MSTPlanner.planMST` 内联」）。

生产虽传非 null `level`，但**后两种失败回退仍可真触发**。

**性质**：不是「绕过工厂 new 旧类」，而是**条件性旧算法逻辑仍在生产链**。
**评估**：这是**合理的兜底**（宁可退化也不抛异常），建议保留但加日志计数。

---

### G. AB 双跑已失去对比意义

**证据**（质量审查组收尾发现）：
`PathfinderFactory.createClassic` 无条件返回 `BandPathfinder` ⇒
`AbObservingPathfinder` 的**两臂都是 Band**。

**后果**：现有 A/B 日志**不能证明**「弹性带比旧 8-pass 更好」—— 两臂同型，对比无意义。

**修法**：要么删掉 AB 通道（旧实现已删，无从对比），要么明确标注「仅用于检测新内核自身不稳定性」。
