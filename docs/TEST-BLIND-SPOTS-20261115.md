## 一、判据与它的局限（务必先读）

**判据**：把 `common/src/test/**` 与 `fabric/src/test/**` 的全部测试源码拼成一段文本，
再逐个检查 672 个生产类**类名是否在这段文本里出现过**。没出现过 ⇒ 记为「盲区」。

**这个判据有三处明确的失真，方向都是「高估盲区」**：

1. **间接覆盖完全不算。** 测试若通过 `Foo` 触达了 `Bar`（`Foo` 内部 `new Bar()`），
   `Bar` 的类名没出现在测试源码里，但它其实被执行了。
   这是最大的一处失真 —— 例如 `RoadData` 被大量测试间接使用，但它自己的类名未必出现。
2. **只按简单类名匹配，不解析 import 与限定名。** 同名类会互相「照亮」，
   而 `pkg.Outer.Inner` 这种嵌套类名根本不会命中。
3. **「出现过」不等于「断言过」。** 测试里 `new Foo()` 之后什么都不 assert 也算「出现」。

⇒ 所以正确的读法是：**把「盲区」理解为「测试代码里连提都没提过的类」**，
而不是「没有被测到的类」。真实覆盖一定高于本清单。

**但这份清单仍然有用**：一个 800 行的类，如果在整个测试目录里连名字都没出现过，
那它**大概率**没有被任何断言约束过 —— 这种「大概率」在 400 个类上重复出现，就是结构性问题。

## 五、按「能不能测」重新分类（这才是可行动的结论）

### A. 结构上测不了 / 不该花力气（约 19,000 行）

- **`mixin` 全部 24 个（992 行）** —— 字节码注入，只能在真机验证。
- **`client` / `map` 的大部分（约 16,000 行）** —— Screen/Widget/Render，需要 Minecraft 客户端环境。
- **`network` 全部 9 个（1,130 行）** —— 网络包编解码理论上可测，但当前无夹具。

> 对这一类，正确的做法是**不追求单测**，而是靠真机验收 + 源码级守卫。
> 本项目已有 6 个源码级守卫（见 `STATUS` 里「6 个源码级守卫全部有效」那条）。

### B. 难测但值得（约 12,000 行）

- `generation`（4,521 行盲区）、`persistence`（2,440）、`decoration`（1,421）——
  需要 `ServerLevel` 或文件系统夹具。文件系统部分（如 `FileBackedAccurateSampleStore`）
  可以先用临时目录测。

### C. ★ 可测且应当补（这是下一步真正该做的）

| 优先级 | 目标 | 理由 |
|---|---|---|
| **P1** | **`pathfinding` 的 6,417 行盲区** | 核心算法（寻路），偏纯计算；`pathlogic` 只 29% 盲区证明这类代码是可测的 |
| **P1** | **`structures` 的 3,127 行盲区** | **批 6 核心**；结构预测/避让是当前正在推进的批次 |
| P2 | `RouteEditorState`（661 行） | 纯状态机（多点折线 + 每段类型），无世界依赖 |
| P2 | `EndpointApproachConnector`（634 行） | 端点接入是几何计算，可为纯函数部分补测 |

> **注意**：不要按「行数从大到小」去挑。`NetworkReuseMerger`（801 行）虽然最大，
> 但它依赖道路存储；`RouteEditorState`（661 行）小一些却是纯状态机，**投入产出比更高**。

## 六、这份清单怎么用

1. **不要**把它当成「59% 代码没测所以项目很危险」—— 见第一节的三处失真。
2. **要**把它当成「下一步补测试时从哪下手」的地图：看 **C 组的四个目标**。
3. 每次补完一个类，重跑本文的脚本，看对应包的盲区率是否下降。
4. 如果哪天想换成真正的覆盖率工具（JaCoCo），本文件应被替换而不是并存 ——
   两个数字口径不同会互相误导。

## 附：本清单的复现方式

```
把 common/src/test/** 与 fabric/src/test/** 的所有 .java 内容拼成一段文本；
对 common|fabric|api|api-fabric 的 src/main/java 下每个类取简单类名，
用 \b 词边界在该文本里做一次匹配；未命中的即为「盲区」。
```

无缓存、无外部工具，纯文本扫描，结果可重复。
