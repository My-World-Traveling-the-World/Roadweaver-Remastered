## 四之三、★ 单跑化的调查结论：**不做**

原计划「`mode == DP` 时跳过旧流水线那 19 个 pass」。动手前读了代码，**判定不能做**：

1. **那 19 个 pass 同时产出 DP 的输入**，不只是修改剖面：`pinnedMask`（:288-292）、
   `startBoundary`/`endBoundary`（:240-274）、`tunnelMask`（:399-414，依赖 `spans`）。
2. **`UnknownEndpointHeightRegistry.lockedHeight` 读旧剖面的锚点站**
   （`int base = profile[anchorStation]`，:80），写进全局 `CHOSEN`，
   **供下一条路当锁定高度**。跳过旧流水线 ⇒ 多条路的接缝高度全变。
3. **`Road.java:182-211` 是「剖面 ↔ 桥隧判定」交替迭代 3~5 轮** ——
   `computeTargetY` 每次输入不同（spans 变了），DP **本来就在这个收敛循环里**。
   所谓「双跑」不是 bug，是「DP 被嵌进了一个更大的迭代」。
4. **收益是毫秒级**：19 个 pass × O(n≈2000 站)，相对道路生成总时长（结构解析 ~300 s）可忽略。

⇒ 按「几秒几秒的不优化」的标准，不值得为它冒「改变多条路接缝高度」的风险。
真正能消除双跑的做法是把那 19 个 pass 重构成「只算输入、不写剖面」，
那是独立的大工程，应单独立项。

### 为什么网络级没接：**契约不匹配，不是没写**

`NetworkPlanner`（现有 6 个规划器的接口）只输出**拓扑**：

```java
List<StructureConnection> plan(List<BlockPos> points, int maxEdgeLenBlocks);
```

而 `RoadPipeline.run(List<RoadNode>)` 输出**拓扑 + 几何**：

```java
record RoadNetworkPlan(List<RoadNode> nodes, List<RoadEdge> edges, List<Integer> isolatedNodes)
  record RoadEdge(... List<BandResult.Point> curve, BandResult band)   // ← 曲线在这儿
```

生成链现在的流程是「规划器给端点对 → A* 现算路径」，
**没有「接收预计算曲线」的入口**。所以接 `RoadPipeline` 必须改生成链，
而且它的拓扑用**测地距离**（而非直线距离）算 MST ⇒ 整张路网形状会变。

⇒ 这个改动**必须真机 A/B 验证**才能决定，不能单方面切。

### 一个矛盾要指出

`metric` / `topology` / `band` / `pipeline` 这 4 个包是 `ArchitectureGuardTest.LAYER_RULES`
**唯一**做了方向约束的包（其余 24 个包没有方向规则）。也就是说：
架构守卫最严的地方，正是**接线最少的地方**。

## 四之七、AB 观测链：从「两个孤岛」到「一条完整的测量链」

`pipeline/ab` 里其实有**两套** A/B 机制，之前只有一套在用，而且用的是差的那套。

### 修掉的第一个问题：观测太粗

| | 之前（`AbObservingPathfinder`） | 之后 |
|---|---|---|
| 输出 | `classic=500(true) band=480(true)` | 四项中立度量 + verdict |
| 能回答 | 点数差多少 | **长度 / 重复XZ / 曲率能量 / 最大转角** 逐项判优劣 |

「点数是 500 还是 480」说明不了新链画得好不好 —— 一条**更短但更弯、重复 XZ 更多**的路
会被这个日志判成「新链更优」。现在用的是 `AbRunner`（原本只有测试在用的那个类）
的 `RouteMetrics` 四项 + `bandRegressed()` + `diffs()`。

为此给 `AbRunner` 加了一个「已有结果」的重载 —— 生产里两条路**已经算完了**，
再走一遍 `solve` 等于把秒级寻路跑第二次。

### 修掉的第二个问题（更要紧）：观测的算法 ≠ 生产的算法

```
BandPathfinder    (bridge, 生产)  自己写了一遍  场求解→回溯→弹性带
BandRouteSolver   (ab,  AB对比)   也写了一遍    一样的东西
```

两份实现服务于不同目的，但**必须是同一个算法**：

| 谁 | 决定什么 |
|---|---|
| `BandPathfinder` | 真机上的路画成什么样 |
| `BandRouteSolver` | 「新链比旧链好还是差」的结论 |

一旦漂移，AB 就对着一个**真实生产里并不存在的算法**做评价 —— 报告仍然全绿，
但结论已经与真机无关。**这类观测失真比没有观测更危险**，因为它给人虚假的确定感。

修法：`BandPathfinder` 改为委托 `BandRouteSolver` 求解单条路线，
自己只保留它独有的那段（点列还原成 BlockPos、取地形高度、端点精确落回）。

### 结果

`[C]` 测试孤岛 **5 -> 3**（`AbRunner`、`BandRouteSolver` 双双出列）。

### `[C]` 剩下三个的性质

| 类型 | 性质 | 处理方向 |
|---|---|---|
| `RoadPipeline` + `QualityGate` | **绑定的一对**：质量门是网络级流水线的配套。它俩未接线是因为**契约不匹配**（`RoadPipeline` 给「拓扑 + 几何曲线」，而生成链只收端点对），不是设计有问题 | 需改生成链 + 真机 A/B，暂缓 |
| `AvoidanceObstacleField` | **缺消费者**，不是重复。它是 **1:1 精细网格**的障碍场采样器（含「代管 PlanningSnapshot 作用域」这个独有能力），而 `BandPathfinder` 需要的是**带步长**的粗网格（step=8）。两者互补，不能互相替换 | 待定：要么给 1:1 网格找消费者，要么删 |

## 四之九、★ 网络级「未接线」的真根因：两个方法没实现接口约定

前面几轮一直把 `RoadPipeline`/`QualityGate` 的孤岛状态归因为「契约不匹配
（它给拓扑+曲线，生成链只收端点对）」。**那只说对了一半。**
更底层的根因是：**接口定义了采样步长，但两个具体实现都没实现它。**

### 缺口一：地形场

```java
// TerrainField.step() 的 javadoc 写得很清楚：
//   真实路线的包围盒动辄 1500×1500，逐格采样是 225 万列 —— 既采不完也存不下。
default int step() { return 1; }
```

但 `GridTerrainField` 作为该接口**唯一的具体实现**，完全没有 step：
数组恒按 `width × depth` 逐格布局、`maxX()` 恒等于 `minX + width - 1`。
于是 `SampledTerrainField.fromAccurateSampler` 只能硬编码 `step = 1`
⇒ 只能用于小区域 ⇒ 网络级规划用不了 ⇒ 整条链路零引用。

### 缺口二：障碍场

`AvoidanceObstacleField` 同样是 1:1：`int x = minX + ix;`（不看 step）。
地形场按 step=8 采样、障碍场按逐格采样 ⇒ **区域尺寸差 64 倍，配不到一起**。

> 所以「`AvoidanceObstacleField` 零引用」不是它没用，是**接不上**。

### 修法（两个提交共 11 个新测试）

| 类 | 改动 |
|---|---|
| `GridTerrainField` | 加带 step 构造器；`height` 就近吸附、`gradient` **除以 step** 归一 |
| `SampledTerrainField` | `of` / `fromAccurateSampler` 各加 step 重载，按 `AccurateHeightGridRequest` 的真实语义折算 **列数**（它的 width 是采样点数、`blockX(i) = minX + (i%width)*step`）|
| `AvoidanceObstacleField` | `sample` / `fromAvoidanceService` 加 step 重载；**只在采样点调判据**（17×17 step=8：9 次 vs 289 次，32 倍）；不传 step 时**默认跟随地形场** |

### 测试钉住的三条最容易悄悄错的地方

1. **梯度不除步长** → 坡度放大 step 倍（step=8 时坡罚炸 64 倍，表现为「平原上也绕坡」，极难看出原因）。用「每 2 格升 2 格 = 坡度 1.0」的斜坡钉住，断言消息里直接写明这个陷阱。
2. **step=1 行为漂移** → 旧构造器必须委托新构造器（step=1），保护所有既有调用方。
3. **方块坐标不吸附** → step>1 时 `height(1,0)`、`height(3,0)` 必须落到最近采样点。

### ★ 我自己的改动差点改坏一条既有语义（原有测试抓住了）

给 `MaskedPotential.potential` 适配 step 时，我把它改成
`soft.potential(minX + snapX(x)*step, ...)`。但 `snapX` 会把**界外坐标 clamp 回边缘**，
于是 `potential(-1,0)` 从 `1.0` 变成「区域内某点的势」（通常是 0）。

而「区域外势为 1.0」是 **`ObstaclePotential` 自己的界外约定**（归一化最大势），
不是随手取的常数。原有测试 `区域外必须视为不可通行` 里那句
`assertEquals(1.0, field.potential(-1, 0), 1e-12)` 立刻抓出来了。

> **教训**：给底层实现加参数时，先看既有测试钉住了哪些**边界语义**。

回归 **695 → 706**。网络级接线现在在技术上成立了 —— 两块拼图（地形场 step、障碍场 step）
都齐了，下一轮可以直接接 `RoadPlanningService`。

## 四之十、★ 网络级内核接线完成：新增 planningAlgorithm = PIPELINE

`[C]` 待办 **2 → 1**（`RoadPipeline` 出列，只剩 `QualityGate`）。
**出厂默认仍是 RNG，零行为变化** —— 这是第六种可选算法，不是替换。

### 接的是什么

现有六种规划器都用**直线距离**决定「哪两个结构该连一条路」。`PIPELINE` 用**测地距离** ——
绕开山和水实际要走多远。两座结构直线 200 格、中间隔一道山脊：
直线距离看不出问题，测地距离会说实话。

```
SampledTerrainField.fromAccurateSampler(step=8)    -> TerrainField
FinslerMetric.of(terrain, ObstacleField.NONE)      -> 度量
RoadPipeline(metric, ElasticBandSolver).run(nodes) -> 拓扑 + 曲线
取 edges -> StructureConnection（丢弃曲线）
```

### 三个必须说清的设计决定

**① 为什么丢掉曲线** —— `RoadPipeline` 还给每条边的弹性带平滑曲线，但生成链现在是
「规划器给端点对 → A* 现算路径」，**没有接收预计算曲线的入口**。要接就得改生成链，
而风险是整张路网形状会变、必须真机 A/B。曲线确实白算了（每条边几十毫秒），
相对「先证明测地距离的拓扑更好」这个大前提是值得的。

**② 为什么用 `ObstacleField.NONE`（有意，不是遗漏）** —— 按结构避让需要
`StructureAvoidanceService` 的规划快照，而那套是**按连接**预算的
（`routeKey(level, connection)`），网络级此刻还没有连接，取不到快照。
后续 A* 走线时避让照旧生效。代价：结构密集区里测地距离可能略乐观。

**③ 为什么 step=8** —— 规划区域动辄 1500×1500，逐格是 225 万列。
step=8 ⇒ 625×625 ≈ 39 万列，与旧 A* 的 `effectiveAStarStep()` 同量级。
**这一条能成立，靠的是上一轮给 `GridTerrainField`/`SampledTerrainField` 补的 step 约定**
—— 两轮的因果关系在这里闭合。

### 三重降级

规划器挂掉会让整局一条路都不生成，比用旧算法严重得多，所以：

| 条件 | 降级 |
|---|---|
| `level == null` | `MSTPlanner.planMST`（直线距离）|
| 地形采样抛异常（区域过大等）| 同上 |
| `RoadPipeline.run` 抛异常 | 同上 |

### 架构代价（守卫逼我如实记录）

新增 5 条跨包依赖边 + 2 条计数增长：

```
planning -> band        1   （ElasticBandSolver，仅为满足 RoadPipeline 构造器）
planning -> bridge      1   （SampledTerrainField）
planning -> metric      3   （FinslerMetric / ObstacleField / TerrainField）
planning -> pipeline    2   （RoadPipeline / RoadNetworkPlan）
planning -> topology    1   （RoadNode）
planning -> core        98 -> 100
planning -> pathfinding 52 -> 53
```

其中 `planning -> pipeline` 正是「接线」本身的含义：**旧链的规划层调用新内核的总装层**。

### 顺带修掉一个环境阻塞

`verify.ps1` 一直用 `--no-daemon`，它会 fork **单次** daemon，而那台机器的单次握手
长期失败（daemon 正常 advertise + 监听 127.0.0.1，客户端连不上就自杀）。
改用 `--daemon`（复用常规 daemon）后同一台机器一次通过，且后续 verify 复用热 daemon 更快。
