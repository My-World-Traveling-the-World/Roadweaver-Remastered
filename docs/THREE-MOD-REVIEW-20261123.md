# 河流、长城、道路联合审查与重构路线（2026-11-23）

这三个模组继续各自运行，有联动时按 **河网计划可用 → 长城计划与占地可用 → 道路** 推进；没装长城时道路仍等已安装的河流。长城保护就绪、墙体实际写入、道路生成结束是三个不同的验收点。现阶段没有理由一并更换三套算法。应先确保失败不会被当成成功，再减少地形重复查询和服务器线程上的工作。

| 优先级 | 结论 | 本轮处理 |
| --- | --- | --- |
| P0 | 河流板块构建失败可以得到一次正常完成通知，区块却没有河网结果；异常被当成无河。 | 合并缓存条目生命周期；需求端至多重试一次，终态失败通知等待方；旧世界收尾不能继续放行区块。 |
| P0 | 长城重开时损坏的计划证据可以被跳过，启动协作方收到成功；仅有地形文件的目录反被误当成墙体计划。 | 按维度读取计划证据；区分合法空计划、缺档、读错和目录枚举失败。恢复不完整时结束长城等待，同时不给初始道路成功信号。 |
| P1 | 道路和长城曾把结构的定位点反算为真实起点区块，定位偏移跨界时会漏查。长城走廊首轮还混用了区块和方块坐标。 | 两侧保留真正的起点区块；定位点仍用于显示。长城初筛使用同一单位与保守边界，精确选择仍按原包围盒。 |
| P1 | 道路跨区块施工重复扫几何，长城根搜索和结构扫描吞掉绝大部分旧预热时间；两者需要不同优化。 | 道路回填直接复用索引指纹，二阶高度回溯只保存每站可行区间的前一高差。长城同区块保护列用四个 64 位字汇总，区块外列单独保留。 |
| P2 | 河流生产代码仍有大类；直接拆洪泛或换队列难以证明河湖没变。 | 分离缓存与诊断、独立河口播种。以拆分前整板产物钉住河段顺序、坐标、高度、宽度及湖面和掩码。 |

## 长城：先重复取样，再处理补建长帧

- **开局主要时间在找起点和避让。** 11 月 22 日 WAYFARING 旧日志 `latest.log:45136,45179,45197,46485–46495`：总 490.551 秒；根搜索 218.460、结构扫描 248.944、精采样 21.152、编译 1.993。该次模板失败 279/291，编译数字不是正常生成的基线。至少这份日志不支持先重写模板摆放或加大精采样并行度。
- **下一次拆分应有清晰的输入。** 把 `RootSearch` 和 `CorridorStructureScan` 的候选生成、去重、真正定位/边界解析分别计数。对相邻、相互重叠的走廊窗口，只枚举一次同结构集的真实起点，同一会话使用原生结构定位并保留跨块起点。若候选主要沿长墙分布，可按区块桶建立窄带索引；高度和距离评分相同的情况保留原顺序。稀疏山脊、宽谷、结构密集区三组对拍整个候选集合、盒子和最后墙线；只对复用的跨窗口查询减量，不重提单点群系预筛。
- **补建限额低于一个区块就无法约束单次长帧。** `WallBodyBackfill` 的 `DRAIN_BUDGET_NANOS` 为 150 ms，`runAll` 仍会处理完整区块；预算在区块之间判断。保留正式模板及高度规则，先统计各区块真实写入量、灯笼/容器写入和 p95/p99，再用已有游标在区块内续跑。必须固定计划版本和区块归属，最后一次方块/实体完成才记完成；取消、卸载和重开要实测。该步骤比更换空间树更针对进游戏后的顿挫。
- **有限范围规则仍有缺口。** `GreatWallConfig#startupSegments` 仍把超过 100,000 格的有限墙限制到启动 4 段，`StartupWallRange#resolve` 用此值截取安全前缀；保护发布后墙体可延后落块。本轮没把它说成“所有有限长度进世界前全部建好”。若恢复这项目标，应先按有限长度分窗复用扫描、管理内存与区块票据，再区分“整条计划已就绪”和“设置范围实际全部落块”，同时为遇海或边界明确终止原因。无限墙保持自己的开局参数。

## 道路：施工做局部；寻路保持粗到精

- **保留现有主流程。** `PipelinePlanner#planTopologyWithin` 先按长度枚举候选，再以粗地形选择连接；每条路线经过 FMM / BAND，在走廊里做精采样、终态避让、桥隧和纵断面判定、保存，最后按区块铺设。施工进度的“道路计划完成”不能解释为所有方块已落。这个链路不需要开局全域方块精采样。长跨海桥正弦、村庄包围盒、终态保护及桥头规则按既有契约；本轮不调高程或桥隧风格。
- **剩余最大的代码优化：给长道路做区块到站点的只读索引。** `RoadChunkPlanCompiler.java:60–92,102–142,171–178`：每区块先归一化道路、准备跨度，再做相交预筛、全站/相邻边筛选、边光栅；长桥跨很多区块时同一条几何被重复巡检。以同版本道路的站点和边 AABB 生成区块候选，桥模板保留 10 格外扩；按原站序喂精确相交和保护判据。权属、共桥、共隧道仍按本次道路集合计算，不能跟单条路的采样索引一起缓存。旧新占地失效要同时覆盖；对拍世界区块的局部站序、方块列、密度、区块边缘、交汇和隧道，再测编译调用次数和 p95。
- **纵断面的优化已落地且仅有夹具口径。** `ProfileDpSolver` 保留原评分、约束、并列顺序，`ProfileParentRow` 依据当前高度和本步高差找上一高度；一般只留一字节前一高差，更多状态用原语整数。在 200 站各 6 个高度、全局 105 个高度、3 个高差的夹具，原始父表数组元素占 252000 B，改后 3582 B（不计对象、其余数组、JVM 开销，未量真机）。这是减少长路内存峰值的依据，不是整个世界的加速比例。已上线的稀疏粗拓扑无需重做；`crossing` 和第二次陆地松弛保留，等真机有覆土、桥面与路线质量对照再动。

## 河流：让按需区块尽快得到真实结果，再拆整板

- **线程与缓存。** `PlateRiverCache.java` 现在让预热、按需和同步读取共用同一条发布结果，允许同步任务领取尚未开始的工作；`RiverEngine#whenPlatesReadyNear` 在首次终态异常即通知区块。旧日志 `latest.log:44839–44852` 的一个河流预热批次记录 144 板、内部计时 190 ms；只适用当时采样器与配置。后续可让 `ChunkStepDefer` 在未命中时复用一次邻板列表（就绪快路径仍保持轻量），并分别测真实排队、计算、回调与磁盘命中。优先看飞行新地带是否少等，不能用该计时推断飞行体验。
- **整板阶段。** 本轮先分出 `PlateOutletSeeds`，保留海面/实际海拔探测、原邻居顺序与入队顺序。下一步分为地形格与出口、Priority-Flood 与流向、湖掩码/出口、河链与收尾，阶段之间只传必要数组。已有原语最小堆；“堆加 FIFO”的洪泛候选只能先做负控和等高平台顺序对拍，不能凭复杂度替换默认。另保留河网连边选项：`StreamsConfigFabric` 的 `connectNearbyWater` 默认关闭，不按开局默认热点排。
- **施工阶段。** `RiverCarverFeature` 仍应按河槽/岸边、地表重铺、方块变更与流体调度拆开，先冻结真实区块方块、含水状态、后续刻与接缝，再动内部写入顺序。河流代码还剩 4 个生产文件超过 1000 有效行：`NetworkTracer` 3504、`RiverCarverFeature` 3213、`StreamsConfigFabric` 1326、`OpenCLAccurateProgram` 1061。同口径扫道路 729、长城 281、河流 205 个生产 Java 文件，前两仓无超限。统计不含纯注释与空行。

## 验收顺序

1. 用相同种子、配置、JDK 和模组组合分别跑新建与重开。记录河网板块冷/热、长城根搜索/结构/精采/编译、道路连接/粗规划/走廊/施工时间；单列线程等待与计算。长城恢复失败时核对道路不在未知保护区域开工。
2. 在原存档副本去出生点东侧长跨海桥、长城端口、河岸和村庄道路交汇实看；用 H 地图对线路，对地面看桥头、半砖缓坡、墙洞及完整落块。另跑河流＋道路、各自单装和重开，不把离线结果等同整包加载。
3. 游戏内按同一路径飞行，采区块准备与真实施工的 p50、p95、p99；关注服务器 tick 和客户端帧时的时间对应。数据先用于判断长城补建游标、道路区块索引和河流列表复用的先后；不凭离线夹具报告游戏 FPS 或整体加速。
