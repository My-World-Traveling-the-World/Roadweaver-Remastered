# RoadWeaver 旧版「施工与方块放置」功能域盘点

> 依据：`D:\云游四海-Mod源码\roadweaver`，HEAD `2c6547a683f6219a5b7c9c4d9f871a77cf3751e0`；只读静态源码盘点，未启动游戏。默认值以当前字段/常量实值为准，不采用源码里的历史注释数字。
>
> 总链路：**规划产出 `RoadData`（含 `targetY` 剖面 + `spans` 跨度）→ 逐段（segment）算施工高度 → 逐列（column）判三态保护 → 放方块 / 清上方 / 垫路基 → 打台账**。施工侧**不重新决定「这里该不该架桥」**，只消费规划期的跨度结论；唯一的例外是运行期桥提升（见 §五）。
>
> 关键分界：**规划期**决定「改哪些列」（`RoadConstructionVolumePlanner`），**施工期**决定「怎么改」（`SegmentPaver` + `RoadBlockPlacer` + `AboveColumnClearer`）。两者目前是**两套独立实现**，只在普通路/规划期桥/封闭隧道这三类上实质等价。
>
> **行号口径**：本文行号来自对冻结仓库的静态扫描，**可能有 ±2 行偏差**（方法定义与调用点容易混）。定位请优先按**方法名/符号名**检索，行号仅作快速跳转参考。
>

## 一、单列放置入口 `RoadBlockPlacer`

- **做什么**：把「这一列路面该放什么方块」收敛到一个入口，并在这里统一执行三条硬规则：材料随机选择、贴墙保护、路基重写。
- **关键类**：[RoadBlockPlacer.java](roadweaver/common/src/main/java/net/shiroha233/roadweaver/decoration/system/RoadBlockPlacer.java)（103 行）。
- **入口重载**：3 个。最终都落到 10 参数版 `placeRoadBlock(world, blockBelow, surfacePos, materials, random, cfg, road, clearHeight, stabilizeFallingCap, tunnelBody)`（`:72`）。
- **算法核心**（顺序不可换）：
  1. `PlacementRules.placeAllowedCheck(blockBelow.getBlock())` —— 目标方块被 `RoadFeatureCompat.dontPlaceHere` 判为不可替换时**直接 return**（[PlacementRules.java](roadweaver/common/src/main/java/net/shiroha233/roadweaver/decoration/system/PlacementRules.java) 共 15 行）。
  2. 从 `materials` 里**随机**取一个材料（`random.nextInt(materials.size())`）—— 所以同一段路的材质是随机分布的，不是固定图案。
  3. `GreatWallRoadGuard.blocksFor(Ch.SURFACE, below1)` 为真则 return（跨 mod 保护）。
  4. **`world.setBlock(below1, chosen, 3)` —— 无条件写 `pos.below()`**。这行在文件里出现**两次**（4~6 参重载 `:32`、10 参重载 `:87`），是整个施工域最危险的写法，见 §二。
  5. `tunnelBody ? clearTunnelBoreHeadroom(...) : clearAboveColumn(...)` —— 洞身段禁止向上清空。
  6. `pos.below(2)` 是 `GRASS_BLOCK` 时替换为 `DIRT`（防止路面下露出草皮）。
- **⚠️ 关键坑**：第 4 步的「无条件」意味着**调用方必须先做完保护判定**。`PAVE_SURFACE_ONLY` 状态绝不允许走这个入口 —— 否则保护判定等于没做。见 §二。

## 二、三态保护列 `ColumnAction`

- **做什么**：把「这一列的保护情况」压缩成一个三值枚举，让优先级能被单测钉住，而不是散落在调用点的 if 里。
- **关键类**：[SegmentPaver.java](roadweaver/common/src/main/java/net/shiroha233/roadweaver/pathlogic/construction/SegmentPaver.java)（423 行）的 `ColumnAction`（`:49`）与 `classifyProtectedColumn`（`:68`）。
- **三态语义**：
  | 枚举 | 判据 | 处置 |
  |---|---|---|
  | `SKIP` | 路面格本身受保护 | 整列跳过（受保护方块本身不能动） |
  | `PAVE_SURFACE_ONLY` | 只有路基（`pos.below()`）受保护 | 照常铺路面，但**绝不能**重写 `pos.below()` |
  | `PAVE_NORMAL` | 都不受保护 | 走 `placeOnSurface` 全流程 |
- **优先级**：`路面格 > 路基`（`surfaceProtected` 先判）。
- **来历（0.9.033 / O-14「单列保护漏单格洞」）**：原来的写法是 `protectedColumn = 路面格受保护 || 路基受保护`，两种都 `continue`，于是在路面下只要有一个箱子/告示牌这类方块实体，整列路面就被跳过、左右邻列照常铺 ⇒ **驾驶面上出现 1×1 的坑**。三态化就是为了修这个坑，同时保证「路基受保护时铺路面但不动路基」。
- **⚠️ 硬约束**：`PAVE_SURFACE_ONLY` 这条路径**不许走 `SurfacePlacementUtil.placeOnSurface`**，因为那会绕到 `RoadBlockPlacer.placeRoadBlock` 的 `setBlock(pos.below())`，正好把受保护的那一格覆盖掉。窄路径的正确做法是 `AboveColumnClearer.clearAboveColumn(...)` + `setBlock(pos, 材料)`。
- **计数器**：`PAVED_OVER_PROTECTED_ROADBED`（`:40`）统计「铺路面时压过了受保护路基」的次数，配套 `pavedOverProtectedRoadbed()` 只读访问器（`:44`）。这是唯一能判断这条路径在真机上有没有被触发的指标。

## 三、上方清空与洞口/洞身分家 `AboveColumnClearer`

- **做什么**：路面铺好后把「路面以上多余的方块/植被/悬空物」清掉，但**必须区分明挖段与隧道洞身段**。
- **关键类**：[AboveColumnClearer.java](roadweaver/common/src/main/java/net/shiroha233/roadweaver/decoration/system/AboveColumnClearer.java)（612 行）。
- **关键常量**：
  - `MAX_FALLING_SCAN = 128`（`:33`）—— 落石扫描的最大向上距离；
  - `MAX_BUMP_CUT = 12`（`:32`）—— 凸起削平的最大切深；
  - `MAX_SURFACE_CLUTTER_SCAN = 16`（`:34`）—— 地表杂物扫描高度；
  - `MAX_FORCED_CLEAR_LOGS = 64`（`:30`）—— 强制清空日志上限（防刷屏）。
- **两套清空语义**：
  | 入口 | 适用 | 行为 |
  |---|---|---|
  | `clearAboveColumn(world, surfacePos, cfg, road, clearHeight, stabilizeFallingCap, true)` | 明挖段 / 普通路段 | 允许**向上清空**到 `clearHeight`，并处理凸起削平与落石帽 |
  | `clearTunnelBoreHeadroom(world, surfacePos, cfg, road, clearHeight)`（`:242`） | 隧道**洞身段** | **只清洞身净空，绝不把洞顶岩体往上削** |
- **★ 洞身禁止向上清空的理由**：洞身段的「上方岩体本身就是顶板」。如果照明挖段那样向上清空，会把整座山的顶掀掉，隧道变成露天沟。这条是**用户级硬约束**，不是可调参数。
- **其它入口**：`clearExtent(tunnelBody, requestedHeight)`（`:223`）把「该清多高」抽成纯函数返回 `ClearExtent`；`bridgeHeadroom(cfg)`（`:273`）桥下净空；`clearForcedHeadroom(...)`（`:296`）强制清空；`clearTemplateBridgeHeadroom(...)`（`:363`）模板桥专用；`checkAboveColumn(...)`（`:375`）只检查不清空（返回 `ClearanceCheck`）。

## 四、施工高度解析 `SegmentPaver.planGrade`

- **做什么**：把「规划期给的 `targetY` 剖面」翻译成「这一段每一列各放什么高度」，并处理涵洞抬升、横截面压平、坡度邻接。
- **关键类**：[SegmentPaver.java](roadweaver/common/src/main/java/net/shiroha233/roadweaver/pathlogic/construction/SegmentPaver.java)（423 行）。
- **关键入口**：`planGrade(world, seg, segmentIndex, centers, targetY, preserveTunnelGrade, preserveCrossingGrade)`（`:83` 的 7 参版；6 参版在 `:74` 转调）。
- **算法核心**（顺序）：
  1. `RoadHeightInterpolator.batchInterpolate(positions, segmentIndex, centers, targetY)` —— **局部插值**（只看中心线前后各若干站），不是全局拟合。
  2. `preserveCrossingGrade` 为假时调 `RoadConstructionSafety.prepareCulvertDeck(...)` —— 涵洞段把整段抬到「最高水位 + 2」。
  3. `RoadConstructionSafety.sampleTerrain(world, positions)` —— 逐列取真实地表高度。
  4. 横截面压平：**只看隧道豁免**（`preserveTunnelGrade`），**不再被桥/路口的 ramp 带豁免**（0.9.027 / O-08 的修正）。
  5. 压平口径用 `RoadConstructionSafety.resolveRoadCrossSection(heights, terrain, nearestColumnIndex(positions, seg.middlePos()))` —— **中心线最近列**，不是中位数。中位数会让斜坡上相邻站轮流高一格，路面变成 `0,1,0,1` 阶梯。
- **⚠️ 历史坑**：`preserveCrossingGrade` 的覆盖范围原来是「跨度本体 + 桥头 ±`bridgeRampSegments`（默认 4）站」，于是桥头引道整段不压平、每一列各走各的高度 ⇒ 真机上出现**桥头逐列阶梯**。
- **为什么这是热点候选但其实不是**：`batchInterpolate` 的局部窗口只有 `LOCAL_SEGMENT_RADIUS = 2`，即每列只扫 5 段，约 2 万 flops/区块 —— 曾有审计把它列为「施工期重算坡度热点」，实测证明**不是**。

## 五、运行期桥提升 `promoteRuntimeBridges`（安全网，不可删）

- **做什么**：在没有 Streams（河流模组）时，施工期现场判断「这一段水面够宽/够深，必须架桥」，把规划期判成普通路的段提升成桥。
- **关键类**：`RoadConstructionSafety.promoteRuntimeBridges`（在 [RoadConstructionSafety.java](roadweaver/common/src/main/java/net/shiroha233/roadweaver/pathlogic/grade/RoadConstructionSafety.java) 942 行内），调用点在 `PathFeature`。
- **为什么它存在**：规划期的桥判定依据是「采样到的水面宽度/水深」，而这依赖河流模组或高度图；两者任一不可用时规划会判成普通路。若施工期照普通路铺，就会出现**把半边河床填平**的灾难。运行期提升是最后一道安全网。
- **实现要点**：O(窗口) 增量探测 —— 用 `inWindow` 判断该段是否已在窗口内，`RUNTIME_BRIDGES` 做增量去重，**不是每区块全量重算**。
- **⚠️ 曾经的误判**：审计曾把它列为「每区块重算桥范围的热点」并建议删除；读源码后证明它是增量去重、设计必需。**这条安全网不能删。**

## 六、隧道清空台账 `TunnelClearLedger`

- **做什么**：回答一个具体问题 —— 隧道 span 的**洞身站**到底有没有走「向上清空」那条路。
- **关键类**：[TunnelClearLedger.java](roadweaver/common/src/main/java/net/shiroha233/roadweaver/pathlogic/tunnel/TunnelClearLedger.java)（133 行）。
- **三个计数**（一行日志对一段隧道）：
  | 字段 | 含义 |
  |---|---|
  | `bodyStations` | 已建成的洞身站数（岩体本身就是顶的那些站） |
  | `skippedClear` | 洞身站上被**跳过**向上清空的路面列数 |
  | `portalCleared` | 洞口明挖段上照常做了向上清空的路面列数（行为必须与改前一致） |
- **输出时机**：`report` 只在 span 的**最后一站铺完之后**打一行，重复调用不重复打（`SegmentPaver` 在段末判断 `tunnelScope != null && segmentIndex >= tunnelScope.spanLast()`）。
- **生命周期**：计数是**运行期观察、不是持久状态**；`RoadTunnelBuilder.clearAll()` 在存档/维度切换时重置。
- **为什么需要它**：洞身/洞口的清空行为在 0.9.065 被分家，但「分家有没有生效」只能靠计数看 —— 如果 `skippedClear` 恒为 0 而 `bodyStations` 不为 0，说明洞身还在被错误地向上清空。

## 七、保护判定 `RoadConstructionSafety.isProtectedExactConstructionBlock`

- **做什么**：判断「某个精确坐标是否被保护」，供桥面、玻璃穹顶等**非路面**的放置路径复用。
- **关键类**：`RoadConstructionSafety.isProtectedExactConstructionBlock(world, pos, road)`（[RoadConstructionSafety.java](roadweaver/common/src/main/java/net/shiroha233/roadweaver/pathlogic/grade/RoadConstructionSafety.java) `:534`）。
- **调用点**：`BridgeBuilder:91`（桥面）、`RoadTunnelBuilder:1230`（玻璃穹顶）。
- **为什么路面走三态而这里走精确判定**：路面的处置需要区分「跳过整列」与「只铺路面」，所以用 `ColumnAction`；桥面/玻璃是逐格放置，只需知道「这一格能不能动」。
- **⚠️ 这条判定的保护范围来自规划期的 `PlanningSnapshot`**。快照缺失时它必然返回 false（与「这里没有结构」同形）—— 属于施工域的静默降级路径，见 §九。

## 八、路基与支撑

- **做什么**：路面以下是虚空/水/松散材料时把路基垫起来，避免路面悬空。
- **关键位置**：
  - `SegmentPaver` 的 `fillColumn` / `clearColumn` 系列（`RoadConstructionSafety` 内实现）；
  - `RoadConstructionSafety.gradeShoulderSide`（旧版路肩分级，**当前已被停用**，见下）；
  - `RoadBlockPlacer` 的 `below(2)` 草皮替换。
- **★ 路肩已停用**：`SegmentPaver` 在 `:346` 有明确注释「Road shoulders are intentionally disabled. Keep the planned road grade and footprint only; extending side columns caused unwanted parallel fill/cut strips on steep terrain.」`RoadConstructionSafety.gradeShoulders` 在全仓**没有调用方**。⇒ 任何「路肩」相关的规划产出都是死码。

## 九、本域的静默降级清单（重点）

| 位置 | 降级行为 | 与什么同形 |
|---|---|---|
| `PlacementRules.placeAllowedCheck` 返回 false | 直接 return，不放任何方块 | 「这里本来就不该放」 |
| `GreatWallRoadGuard.blocksFor` 返回 true | return | 「长城保护了这里」 |
| `isProtectedExactConstructionBlock` 快照缺失 | 返回 false | 「这里没有受保护结构」 |
| `promoteRuntimeBridges` 水位采样失败 | 不提升（按普通路铺） | 「这里不需要架桥」 |
| `prepareCulvertDeck` 世界为 null / 剖面长度不符 | 直接 return（不抬升） | 「这里不是涵洞」 |

> 这五条里**前三条是良性的**（保护方向正确：宁可不动），**后两条是危险的**（`promoteRuntimeBridges` 不提升会填河床，`prepareCulvertDeck` 不抬升会铺进水里）。施工域的可观测性应该优先补在后两条上。

## 十、规划期 vs 施工期的分工现状（重制版必须知道）

| 类别 | 规划期算不算 | 施工期怎么写 | 是否等价 |
|---|---|---|---|
| 普通路面 | `Kind.ROAD` | `placeRoadBlock` + 三态保护 | ✅ 实质等价（共享 `PlannedSectionBuilder` / `plannedBridge` / `fallingCap`） |
| 规划期桥 | `Kind.BRIDGE_DECK` / `PIER` / `SUPPORT` / `TEMPLATE` | `BridgeBuilder` 系列 | ✅ 实质等价（`f18492b` 手工对齐过 Y） |
| 封闭隧道洞身/洞壁 | `Kind.TUNNEL` | `RoadTunnelBuilder` | ✅ 实质等价 |
| 路肩 | 曾产出 `Kind.SHOULDER` | **施工从不清** | ❌ 规划侧纯浪费（重制版已删） |
| scenic 玻璃穹顶/廊道 | **不覆盖** | `ScenicDomeBuilder` / `BridgeBuilder` 侧向 ±1..3 列 | ❌ 规划漏算 |
| 涵洞抬升 | 规划期已烧进 `targetY` | `prepareCulvertDeck` 再算一次 | ⚠️ 常态一致，配置关闭或世界变水时分歧 |
| 路灯/路牌/浮标 | **不覆盖** | `DecorationPlanner` / `BuoyBuilder` | ❌ 规划漏算 |
| 运行期提升的桥 | 只认规划期掩码 | `promoteRuntimeBridges` 现场长桥 | ❌ 口径换类 |

> ⇒ 「校验算的方块」与「施工改的方块」在**核心三件上等价**，在**附加结构上不等价**。这是重制版批 3 要收敛的边界。
